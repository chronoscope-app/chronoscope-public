# 100,000 events with bloom — local macOS measurements

Baseline: `7fe9b6a719de16299bceae93e646eaf369fc997a`. Results are local Apple M5 measurements, not a cross-platform performance guarantee. No GitHub Actions or hosted runners were used.

## Workload and method

`npm --prefix frontend run test:performance:100k` generates and imports 100 entities × 1,000 events as real SQLite-backed records. Each entity follows a coherent geographic track with one-minute UTC samples, five categories and numeric values. The generator is deterministic. Both builds accepted and retained 100,000 rows, rejected zero, and performed no source aggregation. Import preview plus commit took approximately 2.2 seconds.

The hardware browser comparison used Chrome's ANGLE Metal renderer on Apple M5, a 1,262 × 869 CSS-pixel Cesium canvas, device scale 1 and resolution scale 1. Space-time points, bloom, tracks and vertical trails were enabled. The 512 × 512 effect raster, bloom radius/strength/threshold, point styles, track simplification and display cell limits were unchanged. Public map traffic and terrain were disabled; both builds used the same bundled floor imagery. No other GPU tests or native app playback ran concurrently.

Each build was tested with the default 20,000-marker budget and the full 100,000-marker budget. Exact queries and bloom-bin counts retained all 100,000 source events at both budgets. The full-budget orbit/focus/refresh tests asserted that 100,000 markers actually remained loaded throughout. **Playback uses the application's normal moving 25% time window**, drawing about 25,000 markers at the full budget; it is not simultaneous playback of all 100,000 markers.

Three rounds per budget included idle, seven unchanged refreshes, six changing time filters, 180 moving-focus frames, 180 orbit frames and 180 playback frames. Values below are medians across those rounds. FPS uses animation-frame cadence; CPU render timings cover Cesium preRender-to-postRender submission, not asynchronous GPU execution. Native WebKit results are separate below.

## Hardware browser results

| Markers | Metric | Baseline | Tuned |
|---|---|---:|---:|
| 20,000 | unchanged refresh median | 94.1 ms | 70.5 ms |
| 20,000 | changing-filter median | 242.1 ms | 187.6 ms |
| 20,000 | orbit FPS | 60.0 | 60.0 |
| 20,000 | playback FPS | 55.7 | 56.2 |
| 100,000 | unchanged refresh median | 278.1 ms | 157.4 ms |
| 100,000 | changing-filter median | 248.4 ms | 186.9 ms |
| 100,000 | orbit FPS | 60.0 | 60.0 |
| 100,000 | playback FPS | 53.2 | 55.4 |

At 100,000 markers, unchanged refresh latency fell 43.4% and changing-filter latency fell 24.8%. Playback improved modestly; its median p95 frame interval remained 33.3 ms, so the result does **not** establish stutter-free 60 FPS playback. The 60 FPS orbit tests had approximately 16.7–16.8 ms p95 frame intervals.

Query medians were 1.62 → 1.70 ms (15 local HTTP samples each); this small difference is not evidence of an improvement. Retained JavaScript heap after explicit GC was effectively unchanged, 89.95 → 89.84 MiB. End-of-run isolated Rust server RSS was 892.6 → 629.3 MiB; this is an allocator/process observation, not total application memory or a leak guarantee. Measured main-thread task duration fell in refresh/filter/playback scenarios and did not show a material idle/orbit regression. Raw per-round timings are in [the accompanying JSON](mac-100k-bloom-20261017.json).

## Changes

- Cache track camera poses with a narrow roundoff tolerance. The original exact matrix key treated Cesium's ~1e-14 orientation and sub-micrometer stationary-camera normalization as real motion and repeatedly reprojected the entire dataset. Translation tolerance is 10 micrometers and basis tolerance is 1e-12, measured against the last built pose so movement accumulates. The clipping projection, viewport, data generation, selection and style keys remain exact. A real 1 mm pan and zoom still invalidate the cache.
- Resolve each entity's color once during scene rebuilding instead of parsing the same CSS color once per event. This does not introduce a global color cache or retain old theme overrides.
- Select the exact positive 90th percentile for bloom exposure with bounded three-way selection in typed scratch storage. The fallback selects the same exact rank by sorting the remaining partition. The effect algorithm and pixels are unchanged.
- Skip a worker rebuild using the old display packet when a coherent refresh is about to supply the new packet. Direct mode/theme/terrain/style rebuilds retain their default behavior.
- Avoid resending all retained event IDs when the coherent render snapshot already provides their selection membership. The Rust snapshot intersects membership before allocating/sorting IDs, while preserving requested, rendered, geometry and table selections, lexical order and deduplication under the operation gate.

## Correctness and quality

All 31 local Cesium/browser integration checks and 21 focused Rust integration tests passed. Coverage includes selection, camera changes, time scrubbing/playback, table selection, geometry, heat/density/bloom, terrain, imports and repeated globe/map/space-time imagery transitions. Packet, filter-intent, display-math, effect-math and geodesic tests passed, as did TypeScript/build/format checks.

The percentile test compares against an independent full-sort oracle across empty, random, duplicate, sorted, reverse-sorted, organ-pipe and full 262,144-value inputs, while asserting emission is not mutated. Dense 512-pixel heat/bloom rasters match the previous implementation byte for byte. Settled full-frame captures at both marker budgets had **zero differing pixels**. Capture explicitly finishes the camera-dependent bloom kernel at the fixed camera pose to avoid racing its normal debounce.

The new camera-roundoff regression fails against the old frontend (`roundoffReused: false`) and passes against the tuned frontend, including invalidation on a real small pan. Display tests verify that deferring the old packet still installs the new atlas/density resources.

## Native macOS verification

The release macOS app was rebuilt, launched, and connected using both its CLI and MCP transport. The native canvas was 1,062 × 737 CSS pixels at resolution scale 1.5 (1,593 × 1,105 framebuffer pixels). It therefore differs from the controlled Chrome benchmark.

Native playback remains the limit. A first short baseline read suggested 25.3 FPS, but longer full-cycle observations were lower. Frequent status probes produced median rolling FPS of 21.6 baseline versus 19.2 tuned; fresh-launch sparse probes produced 20.7 baseline versus 23.9 tuned. Those sparse readings were [20.7, 19.7, 24.8] versus [22.7, 27.5, 23.9]. Native status requests flush pending GUI work, so probing cadence is itself part of that workload. The 120-frame windows also overlap during frequent probing. All observations are retained in the JSON; **these results do not establish a reliable native FPS improvement or 60 FPS native playback**. Treat roughly 20–25 FPS as the observed native playback range for this workload, with excursions outside it. CPU render submission p95 medians remained around 12–13 ms; full-cycle MCP query medians were about 0.63 ms for both builds. There were no render/context errors.

Native globe → 2D → space-time checks each retained and drew all 100,000 markers with base imagery present. The base-imagery diagnostic excludes effect atlases, so its layer count is not a bloom count. A separate native bloom on/off capture changed 29,807 pixels, confirming the visible effect. Selecting three queried records produced exactly those three selected records and three native selection markers; clearing selection restored the full display. Direct attached CLI snapshot/query commands each returned an exact count of 100,000. Normal automatic saving was restored after testing, and the tuned app was left open with the full dataset and bloom enabled.

The largest confirmed gains are refresh latency, main-thread refresh work and worker completion time. Native timeline updates still rebuild substantial point/stem/track data, so higher native playback FPS will require further profiling of that update path. The current evidence should not be presented as a universal no-regression guarantee.
