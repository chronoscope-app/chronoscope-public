# Continuous viewport loading — 23 October 2026

2D navigation previously notified the viewport loader only after a 160 ms camera-idle delay. The loader then applied another 180 ms debounce. Continuous movement could therefore keep event details and custom WMTS imagery from loading until the gesture stopped.

Camera changes now request viewport updates immediately. Independent event and imagery queues throttle starts by 120 ms, allow one active load each, and retain only the latest pending camera state. Event results can publish while the camera moves; slow imagery does not hold up event updates. WMTS pages finish and publish before yielding to newer bounds, preserving previously loaded imagery without completing every page for an old viewport. Terrain follows the same resource queue. Scene persistence and idle bookkeeping retain their trailing delay.

Local Linux verification uses the real Rust server, production frontend, and Chromium with SwiftShader. The pointer regression uses a synthetic 3,321-event grid, a localhost WMTS server with 450 ms tile delays, and 350 ms delays on viewport responses. It holds the mouse button throughout movement and supplies Cesium camera-change notifications every 40 ms during the drag, so slow software-GPU frames cannot masquerade as the user pausing. It checks that newly exposed event IDs and nontransparent imagery pixels outside the original raster coverage publish **before mouse release**. It also checks that viewport queries do not overlap and the final viewport settles after release.

The regression is available as `npm --prefix frontend run test:viewport-pan`, and both its browser suite and the scheduler unit suite are included in the local validation inventory. `CHRONOSCOPE_CHROMIUM` selects an installed browser; `CHRONOSCOPE_CLI` can select a CLI built into a shared local Cargo target directory.

The TypeScript/Vite production build, local Rust CLI build, all 18 frontend test entries, 56 existing pan-direction cases, and all nine Streets basemap checks passed. Streets checks cover all three map modes, renderer toggling, offline cache reuse and the desktop CSP. Machine-readable evidence is recorded alongside this document. These are software-rendered Linux checks, not physical-GPU performance measurements. No GitHub Actions workflows or hosted runners were used.

The final regression completed **13 viewport queries, displayed 250 newly exposed Events, and fetched 16 map tiles before mouse release**, with one active viewport query at most. New imagery pixels outside the original raster coverage were verified. The original `main.ts` and `view.ts` from HEAD, built with the same remaining checkout, failed the identical continuous-notification test with **zero viewport queries while dragging**.
